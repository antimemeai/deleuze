# Self-clocking group commit: independent critical reading

2026-10-23. Public literature/source lane. **This paper is a useful workload-model hypothesis, not evidence that tuning is unnecessary for arbitrary gate traffic. Its prototype has reproducible policy defects and its retained results do not support the strongest per-load headlines.** No production policy, dependency or implementation change is selected here.

## What the self-clock model actually assumes

The model uses one serialized flush device with duration `F(K)=F0+K*delta`, a fixed population `N` of clients, think time `Z`, and a client that waits for its own commit before producing its next request. It approximates mean response time with `L≈rho*F`, with default `rho=1.5`, then uses `X=N/(Z+L)` and `K=X*F`. This is a mean-field fixed point, not an exact queueing distribution or a tail-latency bound. The paper explicitly labels its closed-loop competitive bound conjectural in §5. [Paper §§2,5](https://arxiv.org/html/2606.18187v1), [fixed-point code](https://github.com/samyama-ai/group-commit-policy/blob/c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28/group_commit/theory.py).

The threshold `lambda*=2/F0` comes from comparing `sqrt(2*F0/lambda)` with `F0` in a particular scalar cost abstraction. That algebra is valid for the displayed formula. It does not by itself prove a universal policy equivalence: whether a timer matures while storage is occupied depends on timer semantics, actual pending arrivals, idle periods and the flush-cost distribution. The prototype's finite-grid comparison minimizes fixed flush cost plus **mean** completion latency, not an all-arrivals retention objective or a p99/SLO objective. Its reported `lambda` in the closed-loop threshold sweep is the greedy policy's resulting throughput, not independently offered traffic. [Experiment code, especially lines51–76](https://github.com/samyama-ai/group-commit-policy/blob/c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28/group_commit/experiment.py#L51).

For Deleuze, blocking native producer threads are one legitimate closed-loop workload. An externally scheduled gate workload is different: future offered events can exist irrespective of earlier completions. An outstanding-client cap can censor that offered stream into not-sent work; an in-flight gate limit can reject admitted-to-transport work. Neither transforms the original offered population into the paper's lossless fixed-`N` network. Full/failing arrivals, client not-sent work, server-only retention and unknown replies must stay in their respective populations. This is a model-applicability inference, not a claim that every producer is open-loop.

The simulator does not model bounded gate/queue rejection, byte/count caps on greedy batches, heterogeneous content sizes, packing/hash CPU, worker scheduling, transport sessions, ordinary storage errors or recovery of original inputs. Those are relevance boundaries, not reasons to demand a larger production subsystem. A device busy-period effect remains a sensible hypothesis to measure under both workload classes.

## Reproduced prototype defects

These findings concern the exact public prototype at commit `c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28`, not a refutation of correctly implemented ski-rental theory. Reproducer and outputs are retained alongside the originals. Existing tests passed **14/14 in3.07s** using the environment's already-installed NumPy/pytest; no package was installed. The full published synthetic/AWS/PostgreSQL experiments were not rerun.

1. **Timer cost uses a future-dependent earlier flush instant.** `online_cost_abstraction` selects arrivals through the first arrival plus `T`, but sets flush time to the last selected arrival (`theory.py:110–126`). One arrival at time0 with `T=10,F0=1` returns cost1. The stated first-waiter timer flushes at10 and costs11. The code has removed that singleton's entire intentional wait by using knowledge of the arrival trace. The separate closed-form periodic-timer objective and this event-triggered timer are also different policies. [Exact implementation](https://github.com/samyama-ai/group-commit-policy/blob/c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28/group_commit/theory.py#L96).
2. **Ski threshold is checked at arrival instants, not when waiting cost reaches it.** With arrivals `[0,100]` and `F0=1`, the prototype waits to100 and returns cost101; its own offline DP returns2, a **50.5× ratio**. A threshold timer could flush at1 and101, yielding cost4. The missing between-arrival event invalidates treating this implementation as a demonstrated2-competitive algorithm. [Exact loop](https://github.com/samyama-ai/group-commit-policy/blob/c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28/group_commit/theory.py#L115).
3. **The DES ski policy has no threshold-crossing event either.** `simulate('ski',{},FlushModel(1),mode='closed',N=1,Z=0,max_commits=10,warmup_commits=0)` returns zero completed requests. After the first arrival it has no later event that can flush the waiting request. This is distinct from the intentional size-only deadlock already tested by the repository. [DES event scheduling](https://github.com/samyama-ai/group-commit-policy/blob/c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28/group_commit/sim.py#L91).
4. **DES timer behavior is not simply the documented first-waiter timer.** `maybe_flush` declines to arm a timer while storage is busy. At flush completion it can arm a new timer and then immediately start another flush anyway (`sim.py:126–128`), leaving that timer event outstanding. Thus backlog collapse is partly implemented as a policy rule, rather than independently established by the `T<F0` inequality. This is a static source finding; no repaired simulator results are claimed. [Completion branch](https://github.com/samyama-ai/group-commit-policy/blob/c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28/group_commit/sim.py#L116).

No fixes were applied to the acquired reference. Consequently its published open-loop contrast should not be used as a validated numerical policy comparison before the timer/ski implementations and sparse-trace cases are corrected and reevaluated.

## Retained results are weaker than the headline

The original retained JSON provides direct counterexamples to uniform near-optimality language:

| Source result | Aggregate highlighted by the prototype | A retained per-load point |
| --- | --- | --- |
| `results/threshold.json` | Median greedy/best timer overhead1.000390; `H2_pass=true` | `Z=.05`: ratio1.313483, about31.35% greater cost |
| `results/H5.json`, EBS | Median1.012544 | `Z=.02`: ratio1.572149, about57.21% greater cost |
| `results/H5.json`, NVMe | Median.999267 | `Z=.02`: ratio1.013765, about1.38% greater cost |

These are the authors' stored results, inspected rather than regenerated. Passing a median criterion does not establish a bound at every load. `run_threshold` explicitly computes a median and accepts it at≤1.05; the test sweep omits the stored `.05` case. A finite geometric timer grid is the best tested grid choice, not an oracle over every policy. [Threshold results](https://github.com/samyama-ai/group-commit-policy/blob/c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28/results/threshold.json), [device results](https://github.com/samyama-ai/group-commit-policy/blob/c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28/results/H5.json), [test selection](https://github.com/samyama-ai/group-commit-policy/blob/c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28/tests/test_experiment.py).

The PostgreSQL evidence is appropriately described as noisy by the authors. The script runs one ordered delay sweep, not randomized replicated cells; the retained32-client TPS at zero delay is6620.56 versus7397.03 at the best observed200µs delay, a ratio.8950. The two-client file gives1048.49 versus1264.80, a ratio.8290. Those observations do not establish that any particular delay is superior, nor a uniform zero-delay optimum. Real-device modeling samples measured fixed costs into a simulator; that is different from running each policy on the actual device. The benchmark defaults to `fdatasync`, and its timed interval begins after `pwrite`; its fitted marginal therefore reflects that measured flush interval, not a complete logger's per-record cost. [PostgreSQL script](https://github.com/samyama-ai/group-commit-policy/blob/c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28/bench/pg_commit_delay.sh), [flush measurement](https://github.com/samyama-ai/group-commit-policy/blob/c7d80f7d0e63ad1fa6bd4f8dba5853bcf31c5a28/bench/measure_fsync.py).

## Older adaptive roots: evidence and gaps

**Laser2017:** the publisher's accessible abstract says it combines lock-free logging with workload-sensitive grouping in OceanBase, claiming throughput and latency improvements. It does not disclose enough of the policy to reconstruct it. The accessible page references Hagmann1987, Helland et al.'s *Group Commit Timers and High Volume Transaction Systems*, Aether2010, ARIES and scalable NVM logging2014. These are citation fronts, not works newly read by this lane. Neither a full chapter nor an exact Laser artifact was obtained; no comparison to Self-Clocks can responsibly conclude that one disproves the other's actual algorithm. [Publisher preview](https://link.springer.com/chapter/10.1007/978-3-319-63579-8_25).

**Low-Overhead Paxos2017:** §4.3 gives a concrete persistence-feedback rule: initialize a commit interval administratively, then update it to `(old_interval + latest_replica_flush_time)/2`, ignoring a replica considered abnormal. It also describes size-or-interval release. The paper supplies neither a universal stability/tail theorem nor a local open-loop gate-retention guarantee. More importantly, §6 says **all three compared methods already use this group commit**; the tested distinction is piggybacked commit-point metadata versus separate synchronization/asynchronous metadata. Therefore its reported~1.3× throughput result does not isolate the merit of the adaptive interval rule. The experiment uses OceanBase0.4.2, three-way replication,18 machines and a write-only YCSB replacement workload. An exact matching code revision and independent workload arrival-model confirmation remain gaps. [Original PDF](https://d-nb.info/1129780104/34), [publisher full text](https://link.springer.com/article/10.1007/s41019-017-0039-z).

## Consequences for synthesis

A no-intentional-wait, drain-already-ready policy is a reasonable **comparison arm**, as are the current bounded-delay policy and a separately specified adaptive candidate. This lane does not justify promoting any one of them to a universal default. A clean experiment must specify when timers start, how caps/deadlines interact, which records a shared sync acknowledges, and what happens at sparse load and sustained backlog. The comparison must retain actual and scheduled latency distributions, capacity failures, offered/issued/not-sent/server populations and post-timing identities; it cannot substitute closed-loop throughput for all-arrival gate completeness.

The useful lesson is to distinguish amortization by naturally ready work from intentional collection delay, and measure their regimes. The strongest unsupported conclusion would be that a device-only scalar threshold removes the need to study open-loop arrival bursts, capacity or tails. No such conclusion is adopted here.
