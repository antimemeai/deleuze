# Feedback control in interrupt moderation and prediction batching

Study date: 2026-10-23. This bounded lane reads two mechanisms: Linux Net DIM and Clipper's per-container batching controller. It acquires primary documentation, the Clipper paper, and pinned implementation sources. It does not implement or select a controller for Deleuze. [Acquisition, hashes, restoration, and reading depth](../../recon/adaptive-batching-control.md) distinguish retained material from material actually read. No reference program was built or benchmarked.

The useful common pattern is feedback from completed work into a bounded choice of future work. The objectives differ substantially. Net DIM prefers bandwidth and then fewer interrupts; Clipper chooses a batch size against a prediction deadline. Neither source establishes an all-arrival append-and-sync guarantee. A controller that improves successful completion latency by discarding work would change Deleuze's population and fail its capture objective.

| Mechanism | Input signal | Actuator | Decision cadence | Explicit restraint |
| --- | --- | --- | --- | --- |
| Linux Net DIM, v6.12 | Byte, packet, event counters and elapsed time | One of five interrupt-moderation profiles, each containing time and packet thresholds | A qualifying interval of at least 64 events, excluding asynchronous profile application | Greater-than-10% comparison deadband, one-profile steps, edge/top parking and tired cooldown |
| Clipper, pinned source | Remaining earliest deadline; completed batch RPC latency grouped by batch size | Maximum prediction batch size, with exploration or regression estimate | Selection at batch dispatch; asynchronous fit requested after each completed batch datum | 0.92 budget factor; five-sample exploration gate when a maximum-size datum exists; model-dependent estimates |

## Linux Net DIM: bounded hill climbing, without a latency sensor

Tal Gilboa's [primary Net DIM documentation](https://kernel.org/doc/html/v6.12/networking/net_dim.html) describes driver-supplied measurements and driver-applied moderation. The pinned code is Linux v6.12, commit `adc218676eef25575469234709c2d87185ca223a`; this is a reproducible reference revision, not a claim to cover the latest kernel.

The controller has two distinct state machines. Measurement state decides whether to collect an interval, await profile application, or start a fresh measurement. Tuning state decides which neighboring profile to try, when to reverse, and when to park. These are independent of the caller's rate of invoking `net_dim()`.

* **Signal and objective:** [`dim_calc_stats`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/lib/dim/dim.c#L57) derives bytes/ms, packets/ms and events/ms from counters and elapsed microseconds. [`net_dim_stats_compare`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/lib/dim/net_dim.c#L269) first prefers a significant increase in byte rate, then packet rate, then a decrease in event rate. This is lexicographic preference, not a weighted CPU/latency objective. Zero-reference cases receive explicit handling. There is no queue-age, packet-delay percentile, backlog, drop count or CPU-cost input to this comparator.
* **Cadence:** [`net_dim`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/lib/dim/net_dim.c#L350) waits for an event-counter gap of at least `DIM_NEVENTS=64`, computes a comparison, then either schedules a changed profile or starts another interval. A zero-duration sample is rejected. The rate calculation for events uses the constant 64; callers and sample cadence therefore matter if counter gaps overshoot the threshold. The threshold is an event count, not a 64-packet count or a wall-clock update deadline.
* **Actuator:** The four RX/TX and EQE/CQE [profile tables](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/lib/dim/net_dim.c#L15) each contain five choices. For example, RX CQE profiles progress through `(usec, packets)` pairs `(2,256), (8,128), (16,64), (32,64), (64,64)`. Moving one index can change both thresholds. These hardware timer settings cannot be interpreted as a userspace append delay without another model.
* **Noise control:** [`IS_SIGNIFICANT_DIFF`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/include/linux/dim.h#L22) requires the integer percentage difference to exceed 10. Small changes are treated as the same. [`net_dim_decision`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/lib/dim/net_dim.c#L297) reverses a climbing direction when a sample is not better, including a tie. It detects a local top using directional step counts, or parks at a profile edge. After ten successful steps without parking it enters tired parking; subsequent decision intervals decrement the tired counter before exploration resumes. This bounds repeated search but does not estimate statistical confidence.
* **Parking reference:** While remaining parked on top, the stored comparison baseline is preserved, rather than replaced on every same-result sample. A significant change against that reference exits parking and tries a neighbor. Tired parking is a cooldown across measurement decisions, not an independent wall-clock timer. The shared [`dim.c`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/lib/dim/dim.c#L8) contains the direction/top/parking helpers.
* **Application boundary:** On change, measurement enters `DIM_APPLY_NEW_PROFILE` and schedules driver work; it does not sample through that state. The selected [`mlx5` callback](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/drivers/net/ethernet/mellanox/mlx5/core/en_dim.c#L36) calls the device moderation operation and resets measurement state. This call site does not inspect a return result. This is a source observation, not a reproduced hardware failure. The controller's correctness depends on supplied counters and successful, timely application.

Inference for append+sync: the small candidate set, comparison deadband, and explicit application state offer understandable controls on search cost and measurement contamination. Its exact objective does not transfer. Increasing completion bandwidth can coexist with growing retention backlog and poor gate-to-retention tail latency. Traffic changes between adjacent intervals can look like a profile effect. At low event rate, 64 events may take a long time; at saturation, interrupt rate is itself altered by the actuator. None of those observations establishes a defect in its networking use case, but each prevents treating its constants as general batching defaults.

## Clipper: paper AIMD differs from the acquired implementation

Daniel Crankshaw, Xin Wang, Giulio Zhou, Michael J. Franklin, Joseph E. Gonzalez and Ion Stoica's [NSDI 2017 paper](https://www.usenix.org/system/files/conference/nsdi17/nsdi17-crankshaw.pdf), §4.3, pp.618–619, defines the target as throughput maximization while batch evaluation latency remains under an SLO. Its default scheme increases batch size additively and reduces it by 10% after an evaluation exceeds the objective. It also studies P99 quantile regression and delayed dispatch. The paper does not specify the additive increment in that section, nor establish an all-arrival retention contract. The delayed-batching discussion separates waiting for more arrivals from choosing a maximum batch size.

**The acquired code is not that AIMD implementation.** Repository HEAD resolved on acquisition to `9f25e3fc7f8edc891615e81c5b80d3d8aed72608`. The following describes this exact source, without claiming it is the paper's evaluated revision. No historical revision implementing paper AIMD was identified in this bounded lane.

* **Budget:** [`ModelQueue::add_task`](https://github.com/ucbrise/clipper/blob/9f25e3fc7f8edc891615e81c5b80d3d8aed72608/src/libclipper/include/clipper/task_executor.hpp#L135) creates a system-clock deadline when the task joins the model queue. At dispatch, the earliest queued deadline is passed to [`ModelContainer::get_batch_size`](https://github.com/ucbrise/clipper/blob/9f25e3fc7f8edc891615e81c5b80d3d8aed72608/src/libclipper/src/containers.cpp#L128). The controller computes remaining microseconds and multiplies by 0.92 to leave slack. An explicitly configured batch size bypasses this adaptive choice.
* **Observation boundary:** [`on_response_recv`](https://github.com/ucbrise/clipper/blob/9f25e3fc7f8edc891615e81c5b80d3d8aed72608/src/libclipper/include/clipper/task_executor.hpp#L744) measures from the timestamp established just before serializing/sending the batch RPC to response processing. This includes more than model-kernel execution and excludes earlier model-queue waiting. Queue wait nevertheless consumes the remaining dispatch budget. Neither timestamp is an append/write/sync boundary.
* **Data and fit:** [`add_processing_datapoint` and `fit_estimator`](https://github.com/ucbrise/clipper/blob/9f25e3fc7f8edc891615e81c5b80d3d8aed72608/src/libclipper/src/containers.cpp#L64) keep count/mean/standard deviation by batch size and request an asynchronous fit after each positive completed-batch sample. The fit pools latency variance and regresses batch size on `mean + 3*pooled_std` latency using a linear ridge estimator. A code comment calls this an estimated P99. This is not an empirical P99 or distribution-free tail bound: the shared-variance assumption and a mean-plus-standard-deviation proxy are substantive assumptions. The source fits the inverse direction, from budget to batch size.
* **Selection and exploration:** If the shrunken budget exceeds the maximum latency seen, the controller explores; otherwise it floors the estimator's batch-size result and clamps it to at least one. Its maximum selected size and maximum observed latency are monotonically accumulated in the read path. Exploration holds the maximum size while an existing datum there has fewer than five observations. Below ten it adds one; above that it multiplies by `1 + max(0, Normal(0.1,0.05))` and truncates to an integer. The constructor, [`explore`/`estimate`](https://github.com/ucbrise/clipper/blob/9f25e3fc7f8edc891615e81c5b80d3d8aed72608/src/libclipper/src/containers.cpp#L215), and [constants](https://github.com/ucbrise/clipper/blob/9f25e3fc7f8edc891615e81c5b80d3d8aed72608/src/libclipper/include/clipper/containers.hpp#L91) establish these details. This is not 10% multiplicative decrease after an SLO miss.
* **Low-load probing:** [`ModelQueue::get_batch`](https://github.com/ucbrise/clipper/blob/9f25e3fc7f8edc891615e81c5b80d3d8aed72608/src/libclipper/include/clipper/task_executor.hpp#L149) takes available tasks up to the selected maximum. In exploration mode, it pads a short batch by copying its last task and marking those copies artificial. This supplies full-size processing measurements even with insufficient real work. The read dispatch path does not implement the paper's optional wait-for-more-arrivals timeout.
* **Population and limitations:** [`remove_tasks_with_elapsed_deadlines`](https://github.com/ucbrise/clipper/blob/9f25e3fc7f8edc891615e81c5b80d3d8aed72608/src/libclipper/include/clipper/task_executor.hpp#L247) pops expired tasks before dispatch. This is material to interpreting achieved throughput and latency. The estimator's retained statistics have no forgetting window in the methods read; a past latency maximum can suppress future exploration after a regime change. Wall-clock shifts affect its deadline arithmetic. These are static source observations, not experiments or a comprehensive correctness review.

The source's [container tests](https://github.com/ucbrise/clipper/blob/9f25e3fc7f8edc891615e81c5b80d3d8aed72608/src/libclipper/test/container_test.cpp#L14) exercise batch-size response to synthetic budgets and the estimation branch, plus mean/std calculation. They do not demonstrate a production tail guarantee, workload-shift recovery, or all-arrival accounting. They were read, not run.

## What transfers, and what remains a different problem

These are comparisons to guide later design discussion, not adopted settings:

1. **Name the controlled quantity.** Maximum group records/bytes, intentional collection delay, and maximum queued work are different controls. Neither batch size nor the delay alone bounds gate-to-retention latency. For a Synced completion objective, feedback must include the actual shared sync completion and the waiting work before it; measuring only frame writes controls a different boundary.
2. **Keep offered work in the objective.** Record arrival, retained/failed/unknown outcomes, oldest pending age and backlog alongside successful latency. Clipper's expiry deletion and artificial padding are inappropriate ways to improve or probe an audit capture population. Any future synthetic load belongs to a separate controlled experiment, not fabricated retained events.
3. **Separate service feedback from arrival noise.** Report offered rate and event sizes while measuring group service time, records/bytes, sync duration and waiting age. A bandwidth change during a controller step does not itself show that step helped. Disk contention, runtime scheduling and other adaptive layers can change the observed plant during the same interval.
4. **Bound exploration and distinguish observation from constraint.** Net DIM's profile bounds and cooldown limit search, but no latency sensor enforces a budget. Clipper uses an estimated tail surrogate, which is not a bound. A hard collector wait cap can bound intentional waiting while an adaptive target changes; it still cannot bound storage service or sustained overload. An aged queue should not become an excuse to wait longer or erase pending arrivals.
5. **Retain simple baselines.** Compare any future controller with fixed bounded groups and zero intentional wait across light traffic, sustained saturation, bursts and workload shifts, at the same completion boundary and with exact arrival/outcome reconciliation. Compare cost and tails as well as successful throughput. This lane provides no Deleuze speedup claim.

Coverage closes the two selected source paths and their primary explanatory material. Still unstudied here: historical Clipper AIMD source, newer Linux DIM changes, online stability proofs, storage-device group-sync controllers, and interference between independent feedback loops. TensorFlow Serving's adaptive scheduler was located but not acquired or read deeply; it is not a third mechanism supported by this report. Root's separate storage and completion-driven batching lanes supply different evidence.
